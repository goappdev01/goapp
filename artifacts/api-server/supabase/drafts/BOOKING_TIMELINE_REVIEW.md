## Configuration

Services continue to expose the existing integer `duration_minutes` for simple services. An absent `ui_metadata.timing` means one continuous work phase. Explicit timing uses:

```json
{"version":1,"mode":"phases","resourcesConfigured":true,"phases":[
 {"id":"apply","name":"Apply","durationMinutes":15,"kind":"work","resources":[{"resourceId":"32ee1b91-6119-441c-a8b5-5fce3be552bd","quantity":1,"occupancy":"booking"}]},
 {"id":"process","name":"Process","durationMinutes":35,"kind":"wait","resources":[]},
 {"id":"finish","name":"Finish","durationMinutes":25,"kind":"work","resources":[]}
]}
```

Phase order is service selection order, then phase order within each service. Durations are exact positive integer minutes, with no rounding to 5/15/30 minute cells. A work phase can explicitly name a same-business qualified `staffId`; unspecified work phases resolve a concrete available professional. Only a new wait with `releaseProfessional:true` releases the professional; an omitted or false value remains occupied. Historical receipts retain their committed semantics. Preparation and cleaning are explicit `kind:"work"` phases whenever required; the engine never invents or omits them based on a service title.

An explicitly configured simple mode may include exactly one work phase matching `duration_minutes`. Its professional and resource requirements remain binding; they are never discarded by synthesizing an empty phase. A simple wait phase, multiple phases, or mismatching duration fails closed.

Advanced phases require `resourcesConfigured:true`. This is an explicit declaration that the owner configured all required shared resources, or declared that no shared resource is needed. False or missing configuration rejects advanced timing conservatively. Simple legacy services remain continuous work.

Resources are `businesses.ui_metadata.bookingResources`, an array of `{id,name,capacity,active?}`. Capacity is a positive integer. A resource demand has `{resourceId,quantity,occupancy:"phase"|"booking"}`. Booking occupancy holds the resource for the complete customer visit; identical repeated whole-visit requirements consume the maximum stated quantity once. Other simultaneously active demands add. A wait can keep a chair while freeing staff. Resource capacity checks include every customer's active reservations.

Absolute blocks on business/staff use `ui_metadata.bookingBlocks:[{startsAt,endsAt}]`, with explicit-offset timestamps. An active business shift is required for the entire visit. Work must also fit staff shifts, when configured, and matching service shifts. These are intersections. Adjacent windows may cover a continuous interval, but a genuine gap cannot. Overnight availability uses `start_time:"22:00"`, `end_time:"06:00"`, and `ui_metadata.endNextDay:true`; the stored weekday identifies the starting local day. UTC iteration and the shift IANA timezone handle DST and midnight. Half-open `[start,end)` intervals allow exact adjacency.

## API

All routes require the caller bearer JWT, passed unchanged with the public Supabase key:

- `GET /api/supabase/booking-availability?business_id=UUID&service_ids=UUID,UUID&dateISO=2035-01-01&days=21&datesOnly=true`. Alternatively provide `from` and `to` explicit-offset instants. Optional `staff_id` and `step_minutes` (default 1). `days` is bounded to 31. The range bounds candidate start instants, so a visit can cross midnight. Response: `{version:1,timezone,slots,availableDates}`. Dates-only mode stops at the first available plan per local day. Optional visual spacing still scans every minute and retains the first minute of each available run (for example 11:37) alongside grid alternatives; it never rounds that boundary away.
- `POST /api/supabase/bookings/timeline` with `{business_id,service_ids,starts_at,staff_id?,request_key,notes?,status?,customer_id?,expected_plan?,ends_at?}` returns `[booking]`. The booking owns a canonical `timing_snapshot`. `expected_plan` is the reviewed server availability plan, used only for equality validation; it never replaces the freshly compiled canonical plan. A changed price, duration, assignment, resource or phase sequence returns `409 BOOKING_SELECTION_STALE` before writing. Optional `ends_at` must also match the canonical end. Both values are included in the retry journal; after a committed result, an identical lost-response retry returns the original receipt even if the catalogue changed. Omitted expectations remain compatible with older clients. Omitted customer is the caller; a verified business owner can book for an existing customer explicitly. Missing SQL contract fails closed with `BOOKING_TIMELINE_UNAVAILABLE`.
- RPCs are `go_booking_timeline`, `go_booking_availability`, and `go_create_timeline_booking`. Optional RPC availability parameters also support `p_date_iso`, `p_days`, and `p_dates_only`.

Plans contain `version,staffId,startsAt,endsAt,timezone,totalClientMinutes,totalDurationMinutes,workMinutes,waitMinutes,serviceIds,serviceDetails,totalPrice,currency,resourcesConfigured,phases,workIntervals,resourceIntervals`. Phase entries include `id,name,serviceId,kind,durationMinutes,offsetMinutes,staffId,resources,startsAt,endsAt`. Work entries include `startsAt,endsAt,staffId,serviceId`; resource entries include `startsAt,endsAt,resourceId,quantity`.

## Transactions, compatibility, and access

Transactions lock business then customer (`go-booking:<business>` and `go-booking-customer:<customer>`), including direct booking and catalogue/schedule update paths. Customer attendance occupies the full visit, independently of staff gaps. Create journals its canonical command and request key; retries return the same booking even if catalogue configuration changed afterward. Different commands cannot reuse that key.

Negotiation keeps the original interval until acceptance. It reuses the stored phase/financial snapshot and shifts its intervals rather than recompiling duration from changed services. The accepted update, resource checks, snapshot shift, history/revision update, and QR invalidation form one transaction. Cancellation and terminal statuses release all active occupancy without deleting the receipt or financial/timing snapshot.

Existing rows are never rewritten. A row without `timing_snapshot` projects as one continuous work interval with its original duration; null legacy staff remains a business-wide wildcard. The original GiST parent-span exclusion remains for legacy rows only. New phased rows use the shared checker for all old/new pairings, so processing overlaps are possible without weakening historical busy intervals. Optional Agent1 creation delegates through the same guard, and its old independent insert trigger is removed by this draft.

No caller receives INSERT/UPDATE grants on calculated snapshot columns. Existing participant RLS remains. Private definer routines check identity and business publication, revoke default PUBLIC/anon execution, and pin an empty search path. The private planner also rejects another customer's identity without verified business ownership, excludes only an authorized existing booking, and accepts frozen plans only when they match that booking's stored canonical snapshot. INSERT triggers recompile current catalogue data and preserve the trusted command's ordered service selection and explicit professional preference, rather than trusting incoming snapshots. Authorized owner manual creation does not grant staff global booking/customer access. Professional receipt authorization for an arbitrary phase-specific staff member remains a separate policy/product dependency; this draft does not widen participant reads.
